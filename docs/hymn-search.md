# Hymn search

Title search includes canonical English/Arabic names, hymn IDs, and service-specific names. Matching ignores case, accents, Arabic vowel marks and tatweel, punctuation, alef variants, and the distinction between alif maqsura and ya. Arabic-Indic and Persian digits match Western digits. Displayed names remain unchanged.

Ranking favors exact titles/IDs, then prefixes and substrings, then all query words, then spelling suggestions. Spelling tolerance allows one edit for words of 4-7 characters and two for longer words, including adjacent transpositions. Short words and numeric tokens require exact spelling; fuzzy matching is disabled for long queries. Inputs require at least two normalized characters and are limited to 200 characters. Results retain distinct hymn IDs even when their names are identical, and deduplicate repeated service references.

The optional **Search hymn words** checkbox searches normalized whole-word phrases in published Text-format passages across all available languages, independent of the navigation language. Matches stay within a paragraph/language column; comments, notation, score lyrics, audio, and video are excluded. This is phrase matching, not semantic search or transliteration between Coptic font encodings. Snippets are inert plain text and links include only matching usages unless the title also matches.

There is no published full-text index. On first opt-in search, the provider reads assigned Text records once per unique content ID with at most four concurrent workers. It does not download hymn identities, Hazzat, scores, or media. Successful indexes are cached in memory for five minutes and shared between simultaneous queries for the same provider; failures are not cached. The UI debounces input and ignores stale responses. An incomplete index produces a retryable error instead of incomplete results. Changing navigation language/feed creates a new provider. A pending text download completes even if the query changes or text search is unchecked; it is reused on later searches.

When word search is enabled, title matches appear as soon as metadata and their service summaries are available. A visible live-region message reports the title-match count and that hymn words are still being searched, including when there are zero title matches. The final combined results use the same ranking and deduplication rules. No definitive empty state is shown before word search completes. A word-search failure retains title matches with a specific retryable warning; title/metadata failure uses the general content error. Query, language, provider, and checkbox changes invalidate callbacks from older searches. The two phases reuse service-summary requests.

Results are paginated in groups of ten across seasons and hymns. Previous/Next controls show the page count, and the range summary receives keyboard focus on an explicit page change. Background word results preserve the selected page and do not move focus; a new query, language/provider, checkbox choice, or retry starts at page one. Pagination is local and does not change content downloads or ranking.

Titles, snippets, and service references highlight normalized query matches, or matching words for reordered/fuzzy queries. Highlight ranges map back to the original text so accents, Arabic marks, Coptic characters, and punctuation remain intact. React text nodes and mark elements are used; published content is never inserted as HTML. If a match is only in an undisplayed ID or translation, displayed text need not contain a highlight.

Both initial and background searches show a decorative spinner alongside the announced loading text. Reduced-motion preferences disable its rotation while preserving the visible indicator and message. Search cards, highlights, pagination controls, loading messages, and word-search errors support both light and dark themes.

The first text search can be expensive on a slow/mobile connection. Progressive rendering improves time to title results but does not reduce the text download. A production-catalog browser check on 2026-11-04 loaded 428 assigned Text records, followed by zero additional text requests on the next query. A publisher-generated, versioned search index would be the appropriate next optimization if the catalog grows.

## Coptic input and matching

The Normal/Coptic input-font radio group changes only the search box font. Coptic mode uses the existing `CopticFont` and left-to-right input; it does not convert characters, open a keyboard, change the query, reset results/pagination, or issue requests. Both modes search the same languages. The existing **Search hymn words** checkbox is still required for passage searches.

Published Coptic Text columns use legacy CS-font keys such as `P[oic Vnou]`, `Acpazec;e`, `Pi,rictoc`, and `nen'u,y`. The text index retains column language alongside plain text. Coptic matching folds letter case and whitespace and treats the published `@`/period sentence separators as boundaries, but preserves letter keys such as brackets, semicolon, comma, apostrophe, backtick, colon, and equals. It does not transliterate, convert to Unicode, or apply English fuzzy-word matching to Coptic passages. English/Arabic title and passage normalization remains independent.

Snippets retain the matched passage language, so Coptic snippets always use `CopticFont` with left-to-right layout, regardless of the selected input font or navigation language. Their highlights use the same Coptic normalization and original text offsets. Equal passage text in different language columns remains distinct in the index. Normalized passages remain cached per document, and request concurrency/cache behavior is unchanged.
